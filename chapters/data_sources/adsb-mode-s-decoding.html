30  Decode ADS-B and Mode S data

Authors

Xavier Olive

Junzi Sun

ADS-B and Mode S decoding starts as follows: a receiver hears 1090 MHz pulses, turns them into bits, checks that the bits make sense, and only then obtains something aviation analysts recognise, such as an aircraft address, callsign, altitude, velocity, or selected altitude. This page follows that path from signal to field.

It complements the pages Surveillance systems, which explains why these systems exist operationally, and Flight tracking and surveillance data, which discusses decoded trajectory datasets.

The examples are intentionally interactive. They use a decoding library compiled for WebAssembly called rs1090. For more in depth details, refer to the online book The 1090 Megahertz Riddle [1] or to the more technical documentation of the rs1090 library.

function hexToBits(hex) {
  return hex.split("").flatMap((char) => {
    const value = parseInt(char, 16);
    return [3, 2, 1, 0].map((shift) => (value >> shift) & 1);
  });
}

function fieldRows(value, prefix = "") {
  if (value == null) return [];
  if (Array.isArray(value)) {
    return value.flatMap((item, index) => fieldRows(item, `${prefix}[${index}]`));
  }
  if (typeof value === "object") {
    return Object.entries(value).flatMap(([key, child]) =>
      fieldRows(child, prefix ? `${prefix}.${key}` : key)
    );
  }
  return [{ field: prefix, value }];
}

function decodeMessage(raw, reference = null) {
  try {
    return { ok: true, value: rs1090.decode(raw, reference) };
  } catch (error) {
    return { ok: false, value: { error: String(error) } };
  }
}

function messageSummary(raw) {
  const bits = hexToBits(raw);
  const df = parseInt(bits.slice(0, 5).join(""), 2);
  return {
    bits: bits.length,
    df,
    firstBits: bits.slice(0, 32).join("")
  };
}

  if (df === 0) return "Short air-air surveillance (ACAS)";

function modesCrc(hexWithoutParity) {
  const generator = 0xfff409;
  let rem = 0;
  for (let i = 0; i < hexWithoutParity.length; i += 2) {
    const byte = parseInt(hexWithoutParity.slice(i, i + 2), 16);
    rem ^= byte << 16;
    for (let bit = 0; bit < 8; bit++) {
      rem <<= 1;
      if (rem & 0x1000000) rem ^= generator;
    }
  }
  return rem & 0xffffff;
}

function hex24(value) {
  return (value >>> 0).toString(16).padStart(6, "0");
}

function findIcao24(decoded) {
  const rows = fieldRows(decoded);
  const row = rows.find((d) => /icao24$/i.test(d.field) || /icao/i.test(d.field));
  return row ? String(row.value) : null;
}

function crcStructureSegments(raw, decoded = {}, nBits = null) {
  const fullHex = raw.toLowerCase();
  const bits = nBits ?? fullHex.length * 4;
  const hex = fullHex.slice(0, bits / 4);
  const df = messageSummary(hex).df;
  if (df === 17 || df === 18) {
    const crc = modesCrc(hex.slice(0, -6));
    const parity = parseInt(hex.slice(-6), 16);
    const xor = crc ^ parity;
    return {
      df, bits, family: messageFamily(df), icaoSource: "explicit address field",
      icao24: hex.slice(2, 8),
      crcLabel: "Parity and CRC",
      crcHex: hex24(crc),
      parityHex: hex24(parity),
      xorHex: hex24(xor),
      xorMeaning: "parity matches CRC → we have a valid message",
      segments: [
        {label: "DF/CA", value: hex.slice(0, 2), cls: "field-control"},
        {label: "ICAO24", value: hex.slice(2, 8), cls: "field-icao"},
        {label: "ME", value: hex.slice(8, 22), cls: "field-payload"},
        {label: "PI/CRC", value: hex.slice(22), cls: "field-crc"},
      ]
    };
  }
  const parityStart = bits === 56 ? 8 : 22;
  const crc = modesCrc(hex.slice(0, parityStart));
  const parity = parseInt(hex.slice(parityStart), 16);
  const xor = crc ^ parity;
  return {
    df, bits, family: messageFamily(df), icaoSource: "from address parity",
    icao24: findIcao24(decoded) ?? hex24(xor),
    crcLabel: "Address parity",
    crcHex: hex24(crc),
    parityHex: hex24(parity),
    xorHex: hex24(xor),
    xorMeaning: "recovered ICAO24 address",
    segments: [
      {label: "DF fields", value: hex.slice(0, 2), cls: "field-control"},
      {label: "payload", value: hex.slice(2, parityStart), cls: "field-payload"},
      {label: "AP", value: hex.slice(parityStart), cls: "field-crc"},
    ]
  };
}

30.1 The radio signal

Mode S downlink messages are transmitted at 1090 MHz. At the antenna, they are not hexadecimal strings. They are pulses carried on a radio wave. A Software-Defined Radio (SDR) receiver captures those pulses as a stream of I/Q samples: pairs of in-phase and quadrature voltage measurements taken at regular intervals. The magnitude at each moment represents the signal amplitude, regardless of carrier phase.

A Mode S demodulator looks at that amplitude stream. It first searches for the preamble, a known four-pulse pattern at 0, 1, 3.5, and 4.5 µs, then reads 56 or 112 bits from the pulse-position modulation that follows. In each 1 µs bit interval, energy concentrated in the first half means a 1, energy in the second half means a 0.

The visualisation below shows real frames extracted from a 6 MS/s recording. Use the buttons to switch between examples. The green shaded region is the preamble (8 µs); the blue/red shaded bars show first-half and second-half energy for each bit interval — blue where energy is concentrated, red where it is low.

  });

TipSampling rate and demodulation

Mode S uses 1 Mbit/s pulse-position modulation, so each bit lasts exactly 1 µs and each preamble pulse is 0.5 µs wide. A SDR receiver must sample fast enough to distinguish those half-microsecond intervals. At 2 MS/s there are exactly two samples per bit, just enough to compare the first and second half, but the timing margin is zero and phase alignment is fragile.

The first widely used open-source decoder, dump1090, originally used 2 MS/s for this reason: common RTL-SDR dongles cannot sample much beyond 2.4 MS/s. Later decoders made use of 2.4 MS/s to gain a small timing margin. The trade-off is that the samples no longer align neatly with half-bit boundaries, so demodulators usually test several phase alignments around each preamble candidate.

At higher rates, such as 6 MS/s with receivers like Airspy, SDRplay, or HackRF, each bit spans six samples and each 0.5 µs pulse spans three. The demodulator can then compare energy in the two half-bit intervals with less timing ambiguity, while CRC validation rejects frames whose remaining weak bit decisions are inconsistent.

30.2 Error control and CRC

The last 24 bits of a Mode S frame are used for Cyclic Redundancy Check (CRC) logic, but the exact meaning depends on the message family.

  • ADS-B Extended Squitter (samples 1 to 3) appends a parity/interrogator field that protects the message and includes the aircraft address in the frame.

  • Selective Mode S replies (samples 4 to 7) such as DF 20 and DF 21 use address parity: the parity is combined with the ICAO 24-bit aircraft address. This helps recover or verify the sender, but it does not protect the 56-bit Comm-B payload in the same self-contained way as ADS-B. This is the first reason decoded data can differ between tools: a receiver, a decoder, or a collection network may make different choices about accepting, correcting, or discarding frames.

Caution

We have skipped over a few practical issues in ADS-B decoding. Two caveats are worth keeping in mind:

  1. Decoded fields are not always the same as the raw bits in the frame. For example, latitude and longitude are encoded as compact CPR values (cpr_lat and cpr_lon) and need additional processing before they become ordinary coordinates.
  2. Some decoded floating-point values are displayed with excessive precision. This comes from converting quantities encoded on a small number of bits into floating-point numbers. The actual precision is much lower, so these values can safely be rounded before practical use.

30.5 Compact Position Reporting

ADS-B position messages do not contain latitude and longitude as ordinary decimal coordinates. They use Compact Position Reporting (CPR), a grid encoding designed to fit a useful global position into a small payload. Airborne global decoding needs two recent messages from the same aircraft: one even CPR frame and one odd CPR frame. Local decoding can use a nearby reference position, such as a receiver or airport location.

The intuition is that one CPR frame does not identify a single point globally. It identifies the same fractional position repeated over a grid. An even frame and an odd frame use slightly different grids; when the two are paired, only one neighbourhood is consistent with both reports.

In the real airborne CPR algorithm, even latitude frames use a spacing of 360 / 60 = 6°, and odd latitude frames use 360 / 59 ≈ 6.10°. The formula is written over a 360° modular range, then decoded latitudes outside [-90°, 90°] are rejected or wrapped back into the physical latitude range. The encoded cpr_lat and cpr_lon values are 17-bit fractions, so they range from 0 to 131071; they say where the aircraft falls inside the current latitude and longitude cell, not which global cell it is in. Longitude is similar, except that the number of longitude zones depends on latitude.

cprNL = (lat) => {
  const absLat = Math.abs(lat);
  if (absLat < 1e-12) return 59;
  if (absLat >= 87) return 1;
  const a = 1 - Math.cos(Math.PI / 30);
  const b = Math.cos(absLat * Math.PI / 180) ** 2;
  return Math.floor((2 * Math.PI) / Math.acos(1 - a / b));
}
cprExampleComputation = {
  const scale = 2 ** 17;
  const mod = (value, base) => ((value % base) + base) % base;

  const evenLat = cprExampleDecoded.cpr_lat ?? cprExampleDecoded.lat_cpr;
  const evenLon = cprExampleDecoded.cpr_lon ?? cprExampleDecoded.lon_cpr;
  const oddLat = cprReferenceDecoded.cpr_lat ?? cprReferenceDecoded.lat_cpr;
  const oddLon = cprReferenceDecoded.cpr_lon ?? cprReferenceDecoded.lon_cpr;
  const evenLatFrac = evenLat / scale;
  const oddLatFrac = oddLat / scale;
  const evenLonFrac = evenLon / scale;
  const oddLonFrac = oddLon / scale;

  const evenLatCell = 360 / 60;
  const oddLatCell = 360 / 59;
  const j = Math.floor(59 * evenLatFrac - 60 * oddLatFrac + 0.5);
  let evenLatDecoded = evenLatCell * (mod(j, 60) + evenLatFrac);
  let oddLatDecoded = oddLatCell * (mod(j, 59) + oddLatFrac);
  if (evenLatDecoded >= 270) evenLatDecoded -= 360;
  if (oddLatDecoded >= 270) oddLatDecoded -= 360;

  const lonZones = cprNL(evenLatDecoded);
  const evenLonZones = Math.max(lonZones, 1);
  const oddLonZones = Math.max(lonZones - 1, 1);
  const m = Math.floor(evenLonFrac * (lonZones - 1) - oddLonFrac * lonZones + 0.5);
  let evenLonDecoded = 360 / evenLonZones * (mod(m, evenLonZones) + evenLonFrac);
  let oddLonDecoded = 360 / oddLonZones * (mod(m, oddLonZones) + oddLonFrac);
  if (evenLonDecoded > 180) evenLonDecoded -= 360;
  if (oddLonDecoded > 180) oddLonDecoded -= 360;

  const knownLat = cprExampleKnown.latitude;
  const knownLon = cprExampleKnown.longitude;
  return {
    scale,
    cprLat: evenLat, cprLon: evenLon,
    refCprLat: oddLat, refCprLon: oddLon,
    evenLatFrac, oddLatFrac, evenLonFrac, oddLonFrac,
    knownLat, knownLon,
    evenLatCell, oddLatCell, j,
    latCell: evenLatCell, latIndex: mod(j, 60), latDecoded: evenLatDecoded,
    oddLatDecoded,
    lonZones, lonCell: 360 / evenLonZones, lonIndex: mod(m, evenLonZones), lonDecoded: evenLonDecoded,
    oddLonDecoded, m
  };
}

The first step is to decode the latitude of the (even) message. The absolute latitude value here depends on an unknown integer \(j\):

\[\textrm{lat}_1 = \frac{36,776}{131,072}\cdot\frac{360^\circ}{60} + j \cdot \frac{360^\circ}{60}\]

or equivalently:

\[\textrm{lat}_1 = 1.683472^\circ + j \cdot 6^\circ\]

For the reference (odd) message, the absolute latitude is slightly different since the aircraft is airborne, therefore moving. It writes with another unknown integer \(k\):

\[\textrm{lat}_2 = \frac{20,907}{131,072}\cdot\frac{360^\circ}{59} + k \cdot \frac{360^\circ}{59}\]

or equivalently:

\[\textrm{lat}_2 = 0.973268^\circ + k \cdot 6.101695^\circ\]

Now, we need to find values for j and k for which the two latitude values are almost equal, which happens for \(j = 7\) and \(k = 7\):

\[\textrm{lat}_1 = 43.683472^\circ \qquad \textrm{and} \qquad \textrm{lat}_2 = 43.685132^\circ\]

Longitude uses the same pairing idea, but the number of longitude zones depends on latitude. At this latitude, we have 43 longitude zones for the even frame and 42 for the odd frame. (The number of zones decreases when we go toward the poles.) With a similar calculation, we find the longitude-zone factor \(m = 0\), and we decode:

\[\textrm{lon}_1 = \frac{21,949}{131,072}\cdot\frac{360^\circ}{43} + m \cdot \frac{360^\circ}{43} = 1.401970^\circ + m \cdot 8.372093^\circ = 1.401970^\circ\]

\[\textrm{lon}_2 = \frac{21,426}{131,072}\cdot\frac{360^\circ}{42} + m \cdot \frac{360^\circ}{42} = 1.401149^\circ + m \cdot 8.571429^\circ = 1.401149^\circ\]

NoteWhy 17 bits are enough here

A CPR latitude fraction has 17 bits, but it is not encoding latitude over the whole [-90°, 90°] range. It encodes a fraction inside a small cell. For an even airborne latitude frame, the cell size is 6°, so the angular step is approximately 6 / 2^17 ≈ 0.000046°, or about 5 metres in latitude.

If we encoded latitude directly over [-90°, 90°] with the same angular step, we would need about log2(180 / (6 / 2^17)) ≈ 21.9 bits, i.e. 22 bits.

CPR is a smart trick to compress information by accepting ambiguity in a single frame and resolving it with an odd/even pair or a nearby reference position.

WarningErrors in CPR decoding

Airborne CPR relies on pairing a recent even frame with a recent odd frame from the same aircraft. If the reference frame is stale, the aircraft may have moved far enough that the two CPR fractions no longer point to the same latitude or longitude neighbourhood. The decoded point can then fall into the wrong latitude or longitude zone: still plausible on a map, but displaced by one or more CPR cells.

Surface CPR is slightly different. The ambiguity region is smaller, so a surface position usually needs external context, such as the airport area, receiver location, or another nearby reference. This is acceptable in practice because surface ADS-B is line-of-sight and low power compared with airborne reception: if a receiver sees surface positions, the aircraft is normally nearby and the local airport or receiver context is available.

30.6 BDS inference

Mode S is not only ADS-B. A ground station, typically a Secondary Surveillance Radar (SSR), can selectively interrogate a transponder and request a Comm-B register. The aircraft replies with DF 20 or DF 21; the 56-bit payload is the MB field. Its structure is determined by a Comm-B Data Selector (BDS) code.

For data analysis, Comm-B is attractive because it contains fields that ADS-B often lacks: selected altitude, barometric pressure setting, roll angle, true airspeed, magnetic heading, indicated airspeed, Mach number, vertical rates, wind, temperature, and hazard reports. The catch is that the BDS code is normally in the uplink interrogation, not in the downlink reply observed by a passive receiver.

BDS inference is where Comm-B decoding becomes less mechanical. Unlike ADS-B, many Comm-B replies do not carry the requested BDS code in the downlink. A passive receiver only sees the 56-bit MB payload, so it must test several candidate layouts and ask which interpretation is credible.

A practical inference strategy is staged:

  • try the relevant BDS decoders on the same payload;
  • reject candidates that violate hard structural rules, such as fixed prefixes, status bits, or reserved bits;
  • check physical plausibility among the remaining candidates, for example Mach number below 1, reasonable airspeed, plausible temperature, or selected altitude within the operating envelope;
  • use state consistency when available: recent headings, tracks, speeds, altitudes, or ADS-B state references can help resolve ambiguous cases.
