34.0.1 2.7 — ADS-C: contract-based surveillance (~4 slides)

34.0.1.1 Slide: ADS-C — the contract model

  • Developed by ICAO FANS committee (1983–1991)
  • An ATSU negotiates a contract with the aircraft: what data to send, under what conditions
Contract Trigger
Periodic Fixed interval (e.g. every 10 min over NAT)
Event Altitude change, waypoint passage, lateral deviation
Emergency periodic Same as periodic, activated in emergency mode
Demand Single on-request report

Uplink: PeriodicContractRequest / EventContractRequest with groups array specifying which tags to include and at what modulus (every N reports).

34.0.1.2 Slide: ADS-C downlink tag structure (TLV)

Payload is a TLV sequence: tag_id (1 B) length (1 B) value. All 18 downlink tag types decoded in crates/acars/src/decode/payload/arinc622/adsc.rs → AdscTag enum:

Tag ID Struct Key fields
BasicReport 7 AdscBasicReport lat, lon, altitude_ft, time_secs_past_hour, accuracy_code, tcas_ok
FlightId 12 AdscFlightId id (callsign string)
PredictedRoute 13 AdscPredictedRoute next + next-next: lat/lon/alt_ft/eta_secs
EarthReferenceData 14 AdscEarthAirReference track_deg, ground_speed_kt, vertical_rate_ft_min
AirReferenceData 15 AdscEarthAirReference heading_deg, IAS/TAS, Mach
MeteoData 16 AdscMeteo wind_speed_kt, wind_dir_true_deg, temperature_c
AirframeId 17 AdscAirframeId icao_hex [3 B]
IntermediateProjection 22 AdscIntermediateProjection distance_nm, track_deg, alt_ft
FixedProjection 23 — projected position at a given time

BasicReport alone gives 4D position. PredictedRoute adds FMS intent. MeteoData gives in-situ wind and temperature — no atmospheric model needed.

34.0.1.3 Slide: ADS-B vs ADS-C — full comparison

Feature ADS-B ADS-C
Frequency 1090 MHz VHF / SATCOM (ACARS)
Trigger Automatic Broadcast Negotiated contract
Recipients Everyone in range Single ATSU per contract
Update rate 0.5–2 s Minutes (periodic)
Coverage Ground receivers† Global via satellite
Data richness Position + velocity Pos + route intent + met + AirRef + more
Direction One-way push Bidirectional (uplink sets the contract)
Access Open, crowdsourced ANSP; OpenSky since 2024

34.0.2 2.8 — CPDLC: controller-pilot dialogue (~4 slides)

34.0.2.1 Slide: CPDLC session lifecycle

CPDLC uses a connection model — unlike ADS-B’s broadcast:

Aircraft → ATSU:  CR1  CONNECT REQUEST   (registration, logon facility)
ATSU → Aircraft:  CC1  CONNECT CONFIRM

  ↕  AT1  ATC message elements  (uplink + downlink, any count)

Aircraft → ATSU:  DR1  DISCONNECT REQUEST

24h FANS-1/A statistics: 1,110 CR1 + 427 CC1 + 628 DR1 + 11,155 AT1 rows.

34.0.2.2 Slide: FANS-1/A CPDLC body — UPER structure

AT1 body bytes (UPER, handwritten decoder in arinc622/cpdlc.rs):

AT1 body
  ├── header: msg_id (16-bit), ref_id (optional 16-bit), timestamp (HH:MM:SS, optional)
  └── elements: SEQUENCE OF  (1 mandatory + up to 4 additional)
        each element:
          id:   9 bits  →  index into cpdlc_fans.json catalog
          body: element-specific UPER  →  CpdlcElement.body

Selected common elements:

Element Template Body type
uM6 MAINTAIN [altitude] Altitude (8 subtypes: FL, metres, above/below…)
uM80 CLEARED TO [position] VIA [route clearance] RouteClearance (SEQUENCE with bitmap)
uM117 CONTACT [facility] [frequency] ICAOUnitNameFrequency
dM0 WILCO Null
dM40 CURRENT DATA AUTHORITY [route clearance] RouteClearance
dM48 POSITION REPORT […] PositionReport (20+ optional fields)
uM227 LOGICAL ACKNOWLEDGMENT Null

34.0.2.3 Slide: Route clearance and position report

uM80 / dM40 RouteClearance is a UPER SEQUENCE with a 10-bit optional-member bitmap:

"body": { "route_clearance": {
  "departure": "CYQX",  "destination": "EGLL",
  "route_information": [
    { "published_identifier": "57N020W" },
    { "published_identifier": "58N030W" },
    { "published_identifier": "MIMKU" }
  ]
}}

dM48 PositionReport: position, altitude, ETO at next waypoint, met data, ATC facility, filed speed/altitude, distance to destination, TCAS status — more than any ADS-B frame.

34.0.2.4 Slide: ATN B1 CPDLC — full decode chain example

Real ATN B1 message from a 6-min RTL-SDR VDL2 recording, verified vs. dumpvdl2:

{ "bearer": "vdl2",  "path": "atn",
  "protocol_stack": ["vdl2","avlc","x25","clnp","cotp","ulcs","atn_b1","cpdlc"],
  "message_class": "app_message",
  "summary": "ATN B1 CPDLC: uM117UnitNameFrequency: CONTACT EGTT 129.605 MHz",
  "app": { "protocol": "atn_b1_cpdlc",  "standard": "ATN B1",
           "elements": [{ "id": 117,  "name": "uM117UnitNameFrequency",
                          "template": "CONTACT [unit name] [frequency]",
                          "body": { "facility": "EGTT",
                                    "frequency": "129.605 MHz" } }] } }

The protocol_stack field names every layer traversed. 24h FANS-1/A: unsupported_bodies: 0 across 6,913 rows — full body coverage.

34.0.3 4.2 — ADS-C in practice (~3 slides)

34.0.3.1 Slide: An oceanic flight with ADS-C

Show a trajectory assembled from ADS-C periodic position reports: - Position reports every 10 min (periodic contract) - Event reports at waypoint crossing and altitude change - Compare with ADS-B ground coverage (gap over Atlantic) and ADS-C (continuous)

Highlight: - The predicted route tag tells us the next waypoint and ETO - The met tag gives in-situ wind and temperature (no model needed) - The aircraft intent tag shows FMS lookahead

34.0.3.2 Slide: ADS-C uplink — what the ground sends

  • Contract request tags: periodic interval, event conditions, group selection
  • The ground tells the aircraft exactly what to report
  • Uplink decoded: 12 sub-tag types (all implemented in datalink)

Example uplink:

{
  "summary": "ADS-C uplink: periodic contract every 600s, demand basic+flight_id+predicted_route",
  "app": { "protocol": "ads_c_uplink",
           "periodic_interval": 600, "demand_groups": ["basic","flight_id","predicted_route"] }
}

34.0.3.3 Slide: ADS-C from OpenSky — 24h analysis snapshot

  • 6,303 decoded messages in 24h (OpenSky antenna)
  • Breakdown by tag presence (basic always; met in ~40%; predicted route in ~60%)
  • Oceanic routes: NAT, Pacific, polar
  • Research opportunity: match ADS-C position reports with ADS-B at coast-out/coast-in

34.0.4 4.3 — CPDLC in practice (~3 slides)

34.0.4.1 Slide: Reading a CPDLC session

Show a complete session timeline (from analysis/cpdlc_longer.jsonl):

CR1  Aircraft → CZQX   CONNECT REQUEST   (registration, logon)
CC1  CZQX → Aircraft   CONNECT CONFIRM
AT1  CZQX → Aircraft   uM20: CLIMB TO AND MAINTAIN FL390
AT1  Aircraft → CZQX   dM0: WILCO
AT1  CZQX → Aircraft   uM80: CLEARED ... [NAT track + route]
AT1  Aircraft → CZQX   dM48: POSITION REPORT [4D pos + met + ETO]
     ...
DR1  Aircraft → CZQX   DISCONNECT REQUEST

~1,110 connect requests + ~11,155 message rows in 24h FANS-1/A dataset.

34.0.4.2 Slide: NAT track clearances — dM40 / uM80 route decode

Structured decode of a route clearance:

{
  "name": "uM80RouteClearance",
  "body": {
    "route_clearance": {
      "departure": "CYQX", "destination": "EGLL",
      "route_information": [
        { "published_identifier": "57N020W" },
        { "published_identifier": "58N030W" },
        { "published_identifier": "MIMKU" }
      ]
    }
  }
}

→ We can reconstruct the full intended route, not just the instantaneous state.

34.0.4.3 Slide: CPDLC + ADS-B + ADS-C — the full picture

Combining three sources for a single transatlantic flight: - ADS-B: high-rate trajectory near coast, surface ops - ADS-C: periodic position (10 min) + event triggers over ocean - CPDLC: clearance instructions, route, altitude assignments, facility changes

Together: a coherent narrative from pushback to gate, including: - What ATC instructed - What the crew acknowledged - Where the aircraft actually was (and where the FMS said it was going)

34.0.5 4.4 — AOC and the operational context (~2 slides)

34.0.5.1 Slide: OOOI timeline

Gate departure (QQ: OUT)  → ground roll →
Takeoff (QF: OFF)         → cruise →
Landing (QF: ON)          → taxi →
Gate arrival (QQ: IN)

Precise FMS timestamps, departure/destination pair, often tail + flight number. Enriches the ADS-B trajectory with gate-to-gate lifecycle events.

34.0.5.2 Slide: Weather, ATIS and operational messages

  • B9 ATIS requests: which airport, which letter → monitor ATIS update frequency
  • RA/C1 weather bundles: METAR station observations (grouping by station/time)
  • 5Z slash-fields: /ETA, /IFR level, /Remarks — ops dispatch data
  • Combining with fastmeteo ERA5: in-situ vs model comparison
